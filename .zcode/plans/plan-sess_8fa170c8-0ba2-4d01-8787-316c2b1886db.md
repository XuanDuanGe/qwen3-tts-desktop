## 结论：脚本快、Electron 慢的实际差异

两条路径最后都使用官方 `Qwen3TTSModel.from_pretrained(...)`，不是 renderer 直接调用模型，也不是 IPC 本身拖慢推理。

当前已确认的关键差异是运行配置和进程生命周期，而非模型下载：

| 路径 | 模型 | 设备/精度 | 进程 |
|---|---|---|---|
| 独立诊断脚本 | 之前为 1.7B，且可指定 0.6B | 显式 `cpu` / `float32` | 新建、独占、运行结束即退出 |
| Electron sidecar | 0.6B | 启动参数默认 `auto` / `bfloat16`，再在 runtime 内部尝试降级 | 常驻；旧 Electron 不退出就继续持有旧 Python 模块和模型加载状态 |

最新日志能确认 Electron 的 job、IPC 与 sidecar 都已正常工作，但卡在 `from_pretrained()`。之前的“加载心跳”把 `runtime.load()` 放入了额外 daemon thread；它不能取消底层加载，还会使实际调用方式偏离 WebUI 的“请求工作线程中同步单例加载”模式，并使退出与资源释放不安全。

WebUI 的关键模式是：全局唯一 backend / 单模型实例、FIFO 锁串行包裹 `load + generate`、同模型已加载时直接复用、切换模型时卸载后再同步加载。当前 core 已有单 `QwenRuntime` 和单 worker，但需要把调用方式和运行参数真正对齐。

## 改造方案

### 1. 固定 Electron 开发态 sidecar 的已验证 CPU 配置

修改 `desktop/src/main/engine/paths.js`：

- 开发态显式向 sidecar 传入：
  ```text
  --device cpu --dtype float32
  ```
- 这与已经成功完成 0.6B WAV 生成的验证配置一致；不再让 Electron 和诊断脚本分别走 `auto/bfloat16` 与 CPU/float32。
- 打包态不强行指定 CPU，保留其未来按发行配置支持 CUDA 的空间。
- renderer 不可传入 device/dtype；调用边界仍严格保持 renderer → main → sidecar。

### 2. 按 WebUI 方式让 sidecar 同步管理唯一模型实例

修改 `core/qwen_tts_engine/server.py` 和 `runtime.py`：

- 删除为加载心跳创建的额外 daemon loader thread；
- 在既有 `JobQueue` 的唯一 FIFO worker 中同步执行 `runtime.load()`，与 WebUI 在 FIFO 锁内同步 load/generate 的模型一致；
- 继续使用同一个 `QwenRuntime`：
  - 同 `modelId` 已加载时跳过 `from_pretrained()`；
  - 切换模型时才释放旧模型、GC、加载新模型；
- 增加最小 `is_loaded(model_id)` 判定：
  - 冷模型任务：显示“正在加载模型”；
  - 热模型任务：直接进入“正在生成语音”，不再误显示 10% 加载；
- 在 runtime 日志中记录**非敏感的实际配置**：requested/effective device、dtype、CUDA 是否可用、模型 ID、加载耗时。绝对路径不写入普通日志。
- 保留现有生成结果正确解包与实际 sample rate 保存逻辑。

这不是把模型挪到 main；main 仍然只管理 child process 与固定 IPC，模型只驻留在 Python sidecar 中。

### 3. 让进程生命周期可诊断且避免旧实例竞争

修改 `desktop/src/main/index.js` 与 `desktop/src/main/engine/manager.js` 的最小日志点：

- 记录 sidecar spawn / exit 的 PID，以及开发态使用的已验证运行配置摘要；
- 保留 Python stderr 的逐行 logger 记录；
- 启动完整测试前，停止此前残留的本仓库 Electron/Vite/sidecar 进程，防止多个 0.6B/1.7B 加载实例争用内存；
- 不新增通用 IPC，也不让 renderer 管理进程。

不使用不安全的线程强杀或假装可取消模型加载。真正无法返回的 native 加载若要强制隔离/超时，必须再引入第二层 inference worker process；这超出本次最小改造范围。

### 4. 严格按 Electron 链路验证

完成代码修改后：

1. 用 `.venv` 编译核心；
2. 启动一个新的 Electron dev 实例，确保它使用更新后的 sidecar；
3. 用同一份本地 0.6B 模型通过实际 IPC 提交：
   - `Ono_Anna` / `Chinese` / `大家好，我是锤子猫`；
4. 检查新日志应包含：
   ```text
   runtime load started device=cpu dtype=float32
   runtime load completed ...
   segment completed ...
   job completed ...
   ```
5. 再提交一次同模型任务，确认日志有“复用已加载模型”，没有第二次 `from_pretrained`；
6. 尝试控制 Electron 窗口进行可见 GUI 表单测试；当前 Browser Use 运行时只提供独立 in-app 浏览器，不能附着到原生 Electron 窗口，因此若环境仍不提供 Electron 控制能力，会如实报告，并以实际 Electron 日志 + 同一 main/sidecar IPC 流程验证为准；
7. 运行 `git diff --check`，不运行完整打包构建。

## 不做的事项

- 不把 renderer 改为直接访问 Python、shell、本地模型路径或 ModelScope；
- 不复制 WebUI 的 FastAPI/Gradio 层；
- 不把模型下载改为 Hugging Face fallback；
- 不新增后台预加载。首次冷加载约十余秒是正常体验成本；先保证其配置一致、可完成且同模型后续复用。
